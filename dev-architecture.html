02

Class hierarchy ของ Benefit

ราก Benefit เก็บสิ่งที่ทุกระบบมีเหมือนกัน (ชื่อ ช่วงเวลา สถานะ priority กลุ่มเป้าหมาย เพดานการใช้ กติกาซ้อนกับโปรอื่น) ชั้นกลางแยกตาม "จังหวะทำงาน" ชั้นล่างคือชนิดจริงที่แอดมินสร้าง — เอียง = abstract

  • Benefitราก · ตาราง benefit (STI, คอลัมน์ kind) · ฟิลด์ร่วมตามตารางด้านล่าง
    • CartBenefitประเมินตอนตะกร้า/เช็คเอาต์ · มี rewardSetId + conditions[]
      • Promotionอัตโนมัติ ไม่ต้องใส่โค้ด · ชนะด้วย priority
        • ItemBundlePromotionซื้อคู่/ของแถม · tiers[] = GiftSetGroup (ซื้อ 1/5/10 ลัง) · ต่อยอด Bundle เดิม
        • GroupThresholdPromotionแบรนด์/หมวด (ProductSet) + ยอดขั้นต่ำ → ส่วนลดท้ายบิลเฉพาะยอดกลุ่มนั้น
        • FlashSalePromotionลดตามวัน/ช่วงเวลา · ปรับราคาที่การ์ดสินค้า
      • Couponมี couponCode/ใบ · วงจรชีวิตต่างกันที่ "วิธีรับสิทธิ์ + วิธีกันใช้ซ้ำ"
        • OnlineCouponโค้ดแชร์ได้ · กันซ้ำด้วยประวัติต่อบัญชี (โควตารวม + ต่อคน)
        • CollectibleCoupondistribution = MANUAL (กดเก็บ) | AUTO_MONTHLY (ออกให้วันที่ N) → กระเป๋าคูปอง
        • WelcomeCouponออเดอร์แรก · FirstOrderCondition · 1 สิทธิ์/บัญชี
        • PaperCouponชุดคูปองกระดาษ · ร้านที่ร่วม = เลือกจาก CustomerSet (กลุ่มลูกค้า/ร้านเดียวกับที่ใช้ทั่วระบบ ไม่มี purpose) · ไม่สั่งพิมพ์ · นับก้นคูปองเบิก
      • StarterKitOfferเซตร้านยาเปิดใหม่ · items[] บังคับ/ทางเลือก · audience = B2B
    • LoyaltyBenefitทำงานหลังชำระเงินสำเร็จ · เขียน ledger
      • PointsRuleตัวคูณช่วงแคมเปญ (บวกกัน) + อัตราพอยท์รายสินค้า (SkuPointRate) + กติกาปัดเศษ/หมดอายุ
      • Campaignช่วงเวลา + ProductSet ที่ร่วมรายการ
        • QuotaCampaignราคาแคมเปญ (โหมด SKU: ต่อ SKU · โหมดกลุ่มสินค้า: กติกาเดียวทั้งกลุ่ม) · โควตารวม + ต่อร้าน · พักโควตา 15 นาที
        • LadderCampaignสะสมยอดรายปี · ขอบเขตนับยอด = ทุกสินค้า | ProductSet · tiers[] แต่ละขั้น = threshold + RewardSet + สิทธิ์ที่เหลือ + ฟอร์ม (ตัวสร้างฟอร์ม 4 ชนิดช่อง) · ขั้นที่มีลูกค้าถึงแล้วลบ/แก้ threshold ไม่ได้
    • RaffleEventใช้ RaffleTicket · รางวัลมี mode A (ลุ้นทันที) / B (จับตามรอบ) · ทางเข้าสิทธิ์เปิดปิดได้ทีละทาง
  • RedeemCatalogItemไม่ใช่ Benefit — รายการแลกพอยท์: pointsCost + rewardSetId (ชี้เซตของรางวัลเดิม)

03

เซตที่ใช้ซ้ำ: ลูกค้า · สินค้า · ของรางวัล

CustomerSet ใหม่

  • kind: STATIC (แอดมินเลือกรายชื่อ/นำเข้า) — ทำก่อน · DYNAMIC (filter jsonb เช่น ประเภทลูกค้า=B2B, ซื้อ ≥ X ใน 90 วัน) — ระยะหลัง
  • ไม่มีฟิลด์ purpose (ตัดออก) — สมาชิกคือลูกค้า/ร้าน/สาขาจากทะเบียนเดียว กลุ่มเดียวใช้ได้ทุกที่ ส่วนว่ากลุ่มทำหน้าที่อะไรดูจากตัวที่อ้างถึง (benefit_audience หรือร้านที่รับคูปองกระดาษ) · ถ้าทะเบียนร้าน/สาขาแยกจากบัญชีลูกค้า ให้ CustomerSetMember ชี้ได้ทั้งสองทะเบียน (memberType) — ต้องยืนยัน
  • นำเข้าไฟล์: .csv/.xlsx · คอลัมน์ A รหัสลูกค้า (จำเป็น) + B ชื่อร้าน (ไม่บังคับ ใช้เทียบเตือน) · แถว 1 = หัวตาราง · มี template ให้ดาวน์โหลด · ผลตรวจแยก ผ่าน/ซ้ำ/ไม่พบรหัส/ชื่อไม่ตรง · นำเข้าแบบ “เพิ่ม” ไม่ลบสมาชิกเดิม
  • CustomerSetMember(setId, customerId, source, addedBy, addedAt) PK คู่ · index customerId
  • ลบเซตที่ถูกใช้อยู่ไม่ได้ → isArchived (กู้คืนได้) · หน้ารายการแสดง “ถูกใช้งานใน” = reverse lookup จาก benefit_audience / ร้านที่รับคูปองกระดาษ (เฉพาะรายการที่ใช้งานอยู่) · นำสมาชิกออกต้องเตือนผลกระทบก่อน
  • CustomerSetMember.source = MANUAL | IMPORT | RULE (RULE ใช้เมื่อทำ DYNAMIC) · ชื่อเซตซ้ำไม่ได้ (รวมที่เก็บถาวร) · เซตว่าง (0 สมาชิก) บันทึกได้แต่ใช้เป็น INCLUDE ในรายการที่ ACTIVE ไม่ได้
  • เปลี่ยนสมาชิกมีผลทันทีกับ benefit ที่ผูก (ไม่ snapshot) แต่ benefit_redemption ที่ใช้ไปแล้วไม่ย้อนแก้

BenefitAudience ใหม่

  • (ownerType, ownerId, customerSetId, effect) · effect = INCLUDE | EXCLUDE · ownerType = BENEFIT | REDEEM_ITEM (รายการแลกพอยท์ไม่ใช่ Benefit แต่ต้องมี “ใครแลกได้” ตามหน้าแคตตาล็อก — D-9)
  • ผ่านเมื่อ: ALL หรือ (อยู่ใน INCLUDE ≥ 1 เซต และไม่อยู่ ใน EXCLUDE ใดเลย) — EXCLUDE ชนะเสมอ
  • audienceMode = SELECTED แต่ไม่มี INCLUDE เลย → ไม่ให้เผยแพร่ (validate ตอน ACTIVE)
  • ผูกได้กับ benefit ทุกชนิด รวมถึง RaffleEvent, StarterKitOffer, PointsRule (กลุ่มที่สะสมพอยท์ได้) และ FlashSalePromotion (แทนรายชื่อลูกค้ารายคนเดิม)
  • ข้อยกเว้น: PaperCoupon ไม่มี audience “ใครใช้ได้” (แจกหน้างาน คุมคนถือไม่ได้) — ควบคุมที่ stores เท่านั้น · StarterKitOffer มีเงื่อนไข B2B ตายตัว (ตรวจ customerType) แล้วเลือก audience จำกัดเพิ่มได้ (ไม่ใช้ DYNAMIC เพื่อรอบแรก)

ProductSet ใหม่

  • ProductSetRule(setId, scopeType, scopeValue, effect) · scopeType = SKU | BRAND | CATEGORY
  • resolve เป็นรายการ SKU ตอนประเมิน (cache ตามเวอร์ชันของเซต) — สินค้าใหม่ในแบรนด์เข้าเซตเองอัตโนมัติ
  • ใช้กับ: เงื่อนไขโปร, ขอบเขตแคมเปญ, ตัวคูณพอยท์, ยกเว้นคูปองส่งฟรี (แทน coupon_category_exclusions เดิม)
  • UI เลือกจากกลุ่มเดียวทุกที่ (ProductSetPicker): ขอบเขตโปร (ตัวเลือก “กลุ่มสินค้าที่ตั้งไว้” เคียง SKU/แบรนด์/หมวดเดิม) · แคมเปญสะสมยอด (ทุกสินค้า หรือกลุ่มสินค้า — ไม่มี scope แบรนด์/หมวด/SKU/ยกเว้นรายตัวแยกอีก) · แคมเปญช่วงเวลา+โควตา (โหมด SKU หรือโหมดกลุ่มสินค้า)
  • QuotaCampaign มี scopeMode = SKU (ตาราง quota_campaign_sku: ราคา/ตัวคูณพอยท์/โควตารายตัว) | PRODUCT_SET (productSetId + priceRule ลด %/บาทเดียวทั้งกลุ่ม + pointMultiplier; ไม่มีโควตารายตัว ใช้เฉพาะโควตารวม + ต่อร้าน) · กันซ้ำ: SKU เดียวอยู่ในแคมเปญช่วงเวลาทับกันไม่ได้ทั้งสองโหมด (resolve เป็น SKU ตอนบันทึก)

RewardSet / RewardItem ใหม่

  • RewardSet(id, name, description, isArchived, currentVersionId) 1:N RewardSetVersion(id, setId, version, createdBy/At, changeNote) 1:N RewardItem (STI ตาม kind) — item ผูกกับ version ไม่ใช่ set
  • เซตเดียวกันถูกชี้ได้จากหลายที่ แต่ แก้เซตที่ ACTIVE อยู่ต้องมีเวอร์ชัน — RewardGrant เก็บ snapshot ของที่ให้จริง ณ วันนั้น
  • ประวัติเวอร์ชัน: ดู/เทียบได้ทุกเวอร์ชัน (ใครแก้ เมื่อไร เปลี่ยนอะไร ใช้อยู่ที่ไหน) · ไม่มี rollback เขียนทับ — “ใช้เป็นฐานแก้” สร้างเวอร์ชันใหม่จากเนื้อหาเก่า · ผู้ใช้เลือกอัปเดตทีละรายการ (benefit/RedeemCatalogItem/RaffleCategory เก็บ rewardSetVersionId)
  • RedeemCatalogItem (แคตตาล็อกแลกพอยท์) ชี้ RewardSet แทนการเก็บประเภท/รายละเอียดรางวัลเอง — เหลือเฉพาะ pointsCost, quota, perCustomerLimit, ช่วงเวลา, audience · ประเภทที่แสดงคำนวณจาก item ในชุด · ชนิด item เพิ่ม CREDIT (เครดิตเงินคืน)
  • ขั้นบันไดแคมเปญ / รางวัลลุ้นโชค / ผลตอบแทนโปรเลือก RewardSet ได้ (ตัวเลือกเสริม ยังกรอกเองได้)
  • valueEstimate ต่อ item ใช้คำนวณต้นทุนเฉลี่ย/งบของลุ้นโชค
  • ผู้ใช้ชุด (benefit, benefit_tier, redeem_catalog_item, raffle_prize) เก็บ rewardSetVersionId · หน้าชุดของรางวัลมีกล่อง “ใครใช้ชุดนี้อยู่ · ใช้เวอร์ชันไหน” และปุ่มอัปเดตทีละรายการ · ชุด 1 รายการสร้างจากหน้าที่เลือกได้ (quick-create) · ที่ที่ตั้งรางวัลเองแบบเดิม (ขั้นแคมเปญ/รางวัลลุ้นโชค “ตั้งรางวัลเอง”) ให้สร้าง RewardSet ชนิด ad-hoc ซ่อนจากรายการ เพื่อให้ pipeline ใช้ทางเดียว

    • AccumulationConditionยอดสะสมแคมเปญ ≥ threshold (ขั้นบันได)
    • ChannelConditionONLINE | POS (คูปองกระดาษ)

progress เป็นสิ่งที่ UI ใช้แสดง "อีก 2 ลังรับของแถม" — ไม่ต้องมีโค้ดคำนวณซ้ำฝั่งหน้าเว็บ

05

Pipeline ประเมินสิทธิ์ (ลำดับเดียวทุกชนิด)

ทุก CartBenefit ผ่านด่านเดียวกันตามลำดับ ราคาถูก → แพง ตัดทิ้งเร็วสุด ผลตัดสินที่เซิร์ฟเวอร์เท่านั้น (หน้าเว็บแสดงผลที่ API ส่งมา)

1 · Window
status = ACTIVE และอยู่ใน startAt–endAt (ตัวจำลองสถานะมีสวิตช์ข้ามวันเวลา)
2 · AudienceGuard
ALL → ผ่านทันที ไม่ query · SELECTED → ตรวจสมาชิกเซต (cache) · EXCLUDE ชนะ
3 · Conditions
ทุก Condition ต้องผ่าน (AND) · เก็บ progress ของใบที่ยังไม่ผ่านไว้แสดงผล
4 · Limits
perCustomer / global จาก redemption · QuotaCampaign ใช้ reservation 15 นาที
5 · Resolve
Promotion แย่งสินค้าเดียวกัน → priority สูงสุดชนะ 1 · Coupon เช็ค combinable ทั้งคู่
6 · Apply
RewardItem AT_CART กระจายลง line ไม่หักเกินมูลค่าสินค้า · ค่าส่งเหมา/ยกเว้นตามอัลกอริทึม §4.1
7 · Commit
ตอนออเดอร์ชำระ: redemption + ตัดโควตา + AT_GRANT · idempotent ด้วย (benefitId, orderId)
ผลต่อ UI ฝั่งลูกค้ารายการโปร/คูปอง/ลุ้นโชคที่แสดงให้ลูกค้า = ผล query "benefit ที่ ACTIVE และ (ALL หรืออยู่ในเซต)" — ลูกค้านอกเซตไม่เห็นรายการ และถ้าใส่โค้ด/เปิดลิงก์ตรง เซิร์ฟเวอร์ตอบ "ไม่พบสิทธิ์นี้" (ข้อความที่แน่นอนรอลูกค้ายืนยัน — ดูคำถามใน requirements.html)
06

ตารางข้อมูล (ER สรุป)

ธีม: ตารางที่เป็น "บัญชี/ประวัติ" เป็น append-only ห้าม UPDATE ยอดย้อนหลัง (แก้ด้วยแถวกลับรายการ) ยอดคงเหลือเป็นผลรวมจาก ledger + cache

ตารางกลุ่มคีย์/ฟิลด์สำคัญหมายเหตุ

โครง TypeScript (ย่อ) — ตามแบบ bundle.entity.ts

// models/benefit/benefit.entity.ts
export abstract class BenefitBase {
  @PrimaryGeneratedColumn() id: number;
  @Column({ unique: true }) code: string;
  @Column() name: string;
  @Column({ type: 'enum', enum: BenefitStatus, default: BenefitStatus.DRAFT }) status: BenefitStatus;
  @Column({ type: 'timestamptz' }) startAt: Date;
  @Column({ type: 'timestamptz', nullable: true }) endAt: Date | null;
  @Column({ type: 'int', default: 0 }) priority: number;
  @Column({ type: 'enum', enum: AudienceMode, default: AudienceMode.ALL }) audienceMode: AudienceMode;
  @OneToMany(() => BenefitAudience, a => a.benefit, { cascade: true }) audiences: BenefitAudience[];
  @Column({ default: false }) combinableWithPromotion: boolean;
  @Column({ default: false }) combinableWithCoupon: boolean;
  @Column({ type: 'int', nullable: true }) perCustomerLimit: number | null;
  @Column({ type: 'int', nullable: true }) globalLimit: number | null;
}

@Entity() @TableInheritance({ column: { type: 'varchar', name: 'kind' } })
export abstract class Benefit extends mixin(BenefitBase, StampableEntity) {
  // template method: ทุกชนิดผ่าน pipeline เดียว ชนิดย่อยเติมเฉพาะ conditions / apply
  abstract conditions(): Condition[];
  abstract evaluate(ctx: EvalContext): Evaluation;
}

@ChildEntity() export class OnlineCoupon extends Coupon {
  @Column({ nullable: true, unique: true }) couponCode: string;
  evaluate(ctx: EvalContext) { return evaluatePipeline(this, ctx); }
}

// models/reward/reward-item.entity.ts
@Entity() @TableInheritance({ column: { type: 'varchar', name: 'kind' } })
export abstract class RewardItem {
  @PrimaryGeneratedColumn() id: number;
  @ManyToOne(() => RewardSet, s => s.items) rewardSet: RewardSet;
  @Column({ type: 'int', default: 1 }) qty: number;
  @BahtColumn({ precision: 12, scale: 2, nullable: true }) valueEstimate: number;
  abstract readonly timing: 'AT_CART' | 'AT_GRANT';
}
export interface CartApplicable { applyToCart(ctx: EvalContext): CartEffect; }
export interface Grantable       { grant(ctx: GrantContext): Promise<RewardGrant>; }
ต้อง spike วันแรก (D-8)ts-mixin-extended + abstract class + @TableInheritance ยังไม่เคยใช้ร่วมกันใน repo นี้ — ให้ dev ทดสอบสร้าง migration + query ลูกด้วย Benefit ราก 1 วัน ก่อนล็อกแบบ ถ้าไม่ผ่านให้ใช้ BenefitBase เป็น mixin เฉพาะ StampableEntity แล้วทำ STI ด้วย @Entity ธรรมดา

Module / API / สิทธิ์ใน NestJS

Module (เสนอ)

  • RaffleModule — Event, Prize, Ticket, Draw (A/B), Audit
  • StarterKitModule
  • HomeModule — รวมส่วนของหน้าแรกลูกค้า (Flash, โปร, คูปองที่เก็บได้, แคมเปญ, เซตร้านยา, ลุ้นรางวัล, แลกพอยท์, สถานะของฉัน) เรียก service ของโมดูลอื่นตาม AudienceGuard · แต่ละส่วนมี endpoint ของตัวเอง (โหลดแยก ไม่บล็อกกัน) และส่วนว่างคืน [] เพื่อให้ UI ซ่อนเอง
  • Job (processors เดิม): point expiry รายคืน · auto-monthly coupon · quota reservation expiry · alert 80/95%

Endpoint หลัก (เสนอ)

  • POST /cart/evaluate → โปร/คูปอง/ค่าส่ง/พอยท์ที่จะได้ (ใช้ซ้ำใน checkout และจำลองตะกร้าของแอดมิน)
  • GET /me/benefits?kind= → เฉพาะที่ลูกค้าคนนี้มีสิทธิ์
  • GET /home/{flash|promotions|coupons|campaigns|starter-kits|raffles|redeem|my-status} → ส่วนของหน้าแรก (guest เรียกได้เฉพาะ flash/promotions) · คืน [] เมื่อว่างหรือนอกกลุ่ม — ข้อมูล Hero/หมวด/ข่าว/แบรนด์ใช้ endpoint เดิมของ pmpc
  • POST /me/coupons/{id}/collect, POST /cart/coupons {code}
  • POST /me/points/redeem, POST /me/raffles/{id}/draw (idempotency-key)
  • /admin/customer-sets (+ /:id/members, /:id/import พร้อมรายงานแถว, /import-template), /admin/reward-sets (+ /:id/versions, /:id/versions/:a/diff/:b, /:id/usages, /usages/:ref:upgrade), /admin/product-sets (+ /:id/preview นับ SKU), /admin/benefits/{kind} CRUD + :publish :pause
  • /admin/claims (คิวคำขอ/เบิก), /admin/ledger/points, /admin/raffles/{id}/audit

สิทธิ์ผู้ดูแล (Casbin)

  • ทุกแถว CasbinRule ใหม่ต้องมี SQL INSERT แบบ idempotent สำหรับ prod + ลงตารางในเอกสาร (prod ไม่โหลด fixture)
  • การ approve คำขอรับรางวัล / ปรับพอยท์ / จับรางวัลโหมด B → สิทธิ์แยกจาก write ปกติ

  • ค่าเงินใช้ BahtColumn; ค่าส่งใช้ shipping-cost เดิมตามอัลกอริทึมสินค้าคละ
