คำศัพท์ที่ต้องตรงกัน (Glossary)

คำเหล่านี้ถูกใช้ในเอกสาร mockup และโค้ดคนละความหมายได้ ถ้าไม่ตกลงก่อน ลูกค้ากับ dev จะเข้าใจต่างกัน

คำข้อเสนอความหมาย PROPOSEDในโค้ดต้องถาม
“ลูกค้า”บัญชีร้านยา (Customer) หนึ่งบัญชี — ไม่ใช่ผู้ใช้แต่ละคนที่ loginCustomerร้านหนึ่งมีหลายผู้ใช้ไหม? สิทธิ์นับต่อร้านหรือต่อคน
“ทุกคน”ทุกบัญชีที่ใช้งานได้ตามที่ตกลงaudienceMode = ALLQ-1
“เซต”มี 4 ความหมาย: กลุ่มลูกค้า · ชุดของรางวัล · กลุ่มสินค้า · เซตร้านยาเปิดใหม่ — UI ใช้คำเต็มเสมอ ห้ามเขียนแค่ “เซต”CustomerSet RewardSet ProductSet StarterKitOfferยืนยันชื่อเรียกในเมนู
“สิทธิ์”ต้องแยก 3 อย่าง: สิทธิ์ลุ้น (ticket) · สิทธิ์รับรางวัล (ปลดล็อกขั้นบันได) · สิทธิ์ใช้โปร/คูปอง (โควตาต่อคน)RaffleTicket / ClaimRequest / BenefitRedemption—
“พอยท์” vs “ยอดสะสม”คนละบัญชีเด็ดขาด: พอยท์แลกของได้ ส่วนยอดสะสมใช้ปลดล็อกขั้นบันไดเท่านั้น ไม่ถูกหักเมื่อแลกพอยท์PointLedger / AccumulationLedgerQ-4 (พอยท์เข้าเมื่อไหร่)
“แคมเปญ”ใช้ 2 แบบ: ช่วงเวลา+โควตา และ สะสมยอดรายปี; ตัวคูณพอยท์ช่วงโปรเรียก “ตัวคูณพอยท์” ไม่เรียกแคมเปญQuotaCampaign LadderCampaign PointsRule—
“ยกเลิก”ยกเลิกออเดอร์ (หักพอยท์/ยอดสะสมคืน แต่สิทธิ์โปรที่ใช้ไปแล้วไม่เรียกคืน) ≠ ปิดโปร (PAUSED) ≠ เก็บถาวร (archive)VOID / PAUSED / isArchivedQ-8
“ลบ”เก็บถาวร ยังดูย้อนหลังได้ — ไม่ลบแถวออกจาก DBisArchived—

User story + AC

คลิกที่แถวเพื่อเปิด Card (As a / I want / So that) และ AC · AC ที่ทีมเขียนเพิ่มเองติด PROPOSED · วันงานเป็นข้อเสนอ ยังไม่ผ่านการประเมินร่วมกับ dev ที่รับงาน

06

Example mapping: เลือกกลุ่มเป้าหมาย (FD-2)

ตัวอย่างที่ใช้คุยกับลูกค้าเรื่องที่ตรงใจที่สุด — การ์ดเขียวแต่ละใบแปลงเป็น AC ได้ตรง ๆ

STORY

  • แอดมินตั้งโปรให้ “ทุกคน” หรือ “บางคน”

RULES

  • ทุกคน = ไม่ต้องเลือกกลุ่ม
  • บางคน = ต้องมีกลุ่ม include อย่างน้อย 1
  • exclude ชนะ include เสมอ
  • ตรวจที่เซิร์ฟเวอร์ ไม่ใช่แค่ซ่อนปุ่ม

EXAMPLES

  • ร้าน A อยู่ในกลุ่ม VIP → เห็นโปรและใช้ได้
  • ร้าน B ไม่อยู่ในกลุ่ม → ใส่โค้ดตรงแล้วถูกปฏิเสธ
  • ร้าน C อยู่ทั้ง VIP และ “ติดหนี้” (exclude) → ใช้ไม่ได้
  • โปร “ทุกคน” → ร้านที่เพิ่งสมัครเมื่อวานก็เห็น Q-1
  • เพิ่มร้าน D เข้า VIP หลังเปิดโปร → ใช้ได้ในตะกร้าถัดไป

QUESTIONS

  • Q-1 ทุกคน = ใคร
  • Q-2 คนนอกกลุ่มควรเห็นโปรไหม
  • Q-3 ใครดูแลรายชื่อ / ใหญ่แค่ไหน

ความเสี่ยง และเส้นตัดถ้าตามไม่ทัน

ความเสี่ยง

  • ขอบเขตกว้าง เวลา ~5 สัปดาห์ — 6 โมดูล + ฐานใหม่; ผลของจำนวนคนอยู่ในตารางด้านบน
  • คำถามบล็อกยังไม่ตอบ — Q-1, Q-2, Q-4, Q-5 กระทบ schema และ AC ของหลาย story
  • STI + mixin ยังไม่เคยใช้ใน repo — spike วันแรก (D-8) ถ้าไม่ผ่านเสียเวลา foundation
  • ลุ้นโชคโหมด B + กฎหมาย/ภาษี — งานที่แก้ย้อนหลังยากที่สุด และเปิดจริงต้องผ่านผู้อนุมัติ (Q-5)

  • UAT ลูกค้า 2 วัน — ถ้าลูกค้าไม่ว่างวันที่ 25–26 พ.ย. ต้องเลื่อน go-live (Q-10)

  • โปรโมชั่น 3 ชนิด + ของแถมหลายระดับ · คูปอง 4 แบบ · พอยท์ · แคมเปญ 2 แบบ · ลุ้นโชค · เซตร้านยา
  • หน้าจอตาม รายการหน้า (59 หน้าจอ mockup รวมโมดูลใหม่ “กลุ่มและชุดที่ใช้ซ้ำ” 6 หน้า)

ยังไม่ทำ (ตามเอกสารเดิม)

  • ระบบสั่งพิมพ์คูปองกระดาษ — ทีมการตลาดพิมพ์เอง
  • แปลงยอดสะสมแคมเปญเป็นพอยท์/ส่วนลด
  • แจ้งเตือนพอยท์ผ่าน SMS/อีเมล/LINE (แสดงบนเว็บเท่านั้น)
  • ยกเลิกการแลกพอยท์เอง · เรียกคืนสิทธิ์โปรที่ใช้แล้วเมื่อคืนสินค้า
  • Migrate โปร Bundle เดิม (D-3)

Definition of Done (ทุก story) PROPOSED

  • AC ทุกข้อมี test อัตโนมัติ (pipeline ครอบคลุมกรณีทุกคน / บางคน / exclude)
  • Code review ผ่าน · migration รันบน staging และ rollback ได้
  • ผลคำนวณตะกร้าเดิม (Bundle) ไม่เปลี่ยนตามชุดทดสอบเทียบ
  • เพิ่ม CasbinRule + SQL idempotent สำหรับ prod + ลงตารางในเอกสาร
  • อัปเดต docs/*.md ของโมดูลที่แก้ในรอบเดียวกัน
  • หน้าจอตรงกับ mockup หรือบันทึกส่วนต่างพร้อมเหตุผล
  • ผ่าน UAT ของลูกค้าในข้อที่เกี่ยวข้อง

เช็คลิสต์ Sign-off ยังไม่มีใคร sign

  • ลูกค้าตอบ Q-1, Q-2, Q-4, Q-5, Q-9, Q-10
  • ลูกค้ายืนยันรายการ R1/R2/R3 และเส้นตัด
  • dev lead ยืนยัน D-1..D-8 และประเมินวันงานใหม่
  • ระบุชื่อผู้ sign-off และวัน UAT
